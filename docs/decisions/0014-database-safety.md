# 0014 — Database safety: layered protection against destructive operations on real data

Status: accepted · Date: 2026-10-07 · Follows the M0.3 safety incident (see [`database-safety.md`](../data-model/database-safety.md))

## Context
`migrate:fresh --env=testing` reset the development database. The test-only protections (forced `phpunit.xml`, `TestCase` guard) did not apply to artisan commands, `--env` changes only a label, and the obvious fix (an event listener on `CommandStarting`) is silently disabled by Laravel exactly when the label is `testing`. Documentation alone is not a safety boundary.

## Decision
Defense in depth, each layer independently sufficient for its own failure mode:
1. **Separate restricted PostgreSQL role for the test suite** that owns only `<db>_test` and has no `CONNECT` on the development database. The suite switches to it before the app boots (`tests/bootstrap.php`).
2. **Forced test configuration** in `phpunit.xml` (`<env>` + `<server>`, with `force`).
3. **Live-connection verification** in `Tests\TestCase`: the database and user reported *by the server* must be the test database and the test role.
4. **Guarded destructive commands**: Laravel's `migrate:fresh|refresh|reset|rollback` and `db:wipe` are replaced (container `extend`) by subclasses that call `DestructiveCommandPolicy` for the connection they will really use. The checked database is the **effective** one (`--database`, and `DB_URL`/`url` applied via Laravel's own `ConfigurationUrlParser`). Refused unless the database name ends in `_test` or `TROPHYVAULT_ALLOW_DESTRUCTIVE_DB` equals the exact name; never in production; the environment label is never consulted.
5. Laravel's `DB::prohibitDestructiveCommands()` in production.
6. **Safe wrappers instead of raw commands**: `make db-fresh-test`, `make db-reset-dev CONFIRM=<name>` (read target from the container, require typing it back, refuse data unless `WIPE_DATA=yes`).
7. **CI/compose static checker** (`scripts/check-ci.py`, with a mutation self-test) in the CI docs job.
8. All destructive safety tests run against **nonexistent decoy databases**; real-dev-DB experiments are read-only or marker-based and automatically skipped when the dev database holds data.

Rejected: relying on `--env`/`.env.testing` (label only); a `CommandStarting` listener (not dispatched for label `testing`); a global "allow destructive" boolean (can unlock the wrong target); Laravel's production-only prohibition as the only guard.

## Consequences
- Running `migrate:fresh` on the dev database now requires an explicit, named, deliberate step (`make db-reset-dev`).
- Five command classes replace framework ones; they only add a check before `parent::handle()`. A Laravel upgrade that changes those constructors will fail loudly in the safety tests.
- Local setup needs two extra variables (`DB_TEST_USERNAME`, `DB_TEST_PASSWORD`, generated by `scripts/setup.sh`); CI works without the restricted role because its database contains only test data.
- Existing volumes are migrated by `scripts/ensure-test-db.sh` (it recreates the disposable `*_test` database owned by the test role).
